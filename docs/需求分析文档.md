# 学生简易日报系统需求分析文档

> 文档版本：V1.2  
> 编制日期：2026-07-23  
> 适用项目：`student-simple-daily-report`  
> 文档状态：需求基线（待产品/开发评审）

## 1. 文档目的

本文档用于明确学生简易日报系统改造后的业务目标、用户角色、功能范围、数据模型、权限规则、部署架构、验收标准与迁移要求，并作为产品设计、开发、测试和上线验收的共同依据。

本次改造的核心变化如下：

1. 数据库由本地 SQLite 迁移至 Supabase PostgreSQL。
2. 网站前端部署至 Netlify。
3. 学生继续使用现有的用户名和密码登录，不接入 Supabase Auth；登录接口迁移为 Netlify Functions。
4. 管理员单独使用 Supabase Auth 登录，并通过受保护的管理员模块管理学生用户。
5. 日报不再填写、展示或依据“工作时间/有效时间”进行评价。
6. 每份日报使用四种自我评价状态：满意、一般、不满意、其他。

## 2. 项目背景与现状

### 2.1 现有能力

现有系统采用 React + Flask + SQLite，主要包含：

- 学生账号密码登录、退出及会话检查；
- 学生日报填写与按日期更新；
- 全体学生按日期范围展示的进展看板；
- 日报详情查看；
- 用户新增、删除和密码修改；
- 每日邮件汇总；
- 按工作时间和有效时间计算看板颜色；
- Docker、Nginx 本地或服务器部署方式。

### 2.2 现有问题

- SQLite 文件不适合 Netlify 的无状态部署模式，也不利于多实例并发和云端备份。
- 现有管理员页面为独立 Flask 页面，且未受到管理员登录和角色权限保护，不可直接暴露在公网。
- 学生登录保持现有轻量方式，但管理员入口必须与学生入口隔离并加强权限保护。
- 以工作时间和有效时间推导颜色，不能直接表达学生对当日结果的主观判断。
- “明日计划”被拼接进 `main_work` 字段，不利于查询、校验和统计。
- 邮件收件人依赖本地 CSV 文件，不适合无本地持久磁盘的云端部署。

## 3. 建设目标

### 3.1 业务目标

- 为学生提供简单、快速、移动端友好的日报提交入口。
- 用明确的自我评价状态代替工时评价，降低填写负担。
- 为团队提供直观的跨学生、跨日期日报看板。
- 为管理员提供安全、可审计的用户管理能力。
- 建立适合持续部署和云数据库的运行架构。

### 3.2 技术目标

- 使用 Supabase PostgreSQL 持久化业务数据。
- 学生沿用业务表密码哈希和服务端 Session；管理员使用 Supabase Auth。
- 学生业务数据由 Netlify Functions 访问 Supabase PostgreSQL，不允许浏览器绕过 API 直接写入。
- 管理端直接访问 Supabase 数据时必须使用 Row Level Security（RLS）；特权操作仍由服务端执行。
- React 网站由 Netlify 构建、发布并提供 HTTPS 访问。
- 敏感密钥不得进入前端代码或 Git 仓库。
- 生产环境的数据库变更必须通过可版本化 SQL Migration 执行。

### 3.3 非目标

首期不包含：

- 复杂组织架构、班级和多租户体系；
- 审批流、日报打回和多级审核；
- 积分、排名或绩效考核；
- 即时聊天和评论讨论；
- 原生 iOS/Android 应用；
- 学生自助注册（账号由管理员创建）。

## 4. 用户角色与权限

### 4.1 角色定义

| 角色 | 说明 | 核心权限 |
| --- | --- | --- |
| 学生 `student` | 日报填写者，使用现有系统账号 | 登录、查看看板、查看日报详情、创建或修改自己的日报 |
| 管理员 `admin` | 使用 Supabase Auth 登录的系统维护者 | 查看管理员模块；创建、编辑、启停学生账号；重置学生密码；查看用户状态 |

### 4.2 权限原则

- 学生业务页面必须通过现有学生会话登录后访问。
- 管理员页面必须通过 Supabase Auth 登录，学生会话不能访问管理员页面。
- 学生只能创建和修改自己的日报，不能修改他人日报。
- 已登录学生可以查看所有启用学生的看板、单日日报详情和全部历史日报正文。
- 只有管理员可以调用用户管理相关服务端接口。
- 管理员前端不能直接使用 Supabase `service_role` 密钥。
- 管理员不能停用或降级当前系统中最后一个有效管理员。
- 用户被停用后，应立即或在当前令牌失效后的最短可接受时间内失去访问权限。

## 5. 核心业务规则

### 5.1 日报日期

- 系统业务时区固定为 `Asia/Shanghai`。
- 沿用当前规则：每日凌晨 03:00 为业务日期切分点。
- 00:00—02:59 提交的日报归属前一个自然日，03:00 后归属当天。
- 同一用户同一业务日期最多存在一份日报。
- 重复提交视为更新，不新增重复记录。

### 5.2 自我评价状态

日报必须且只能选择以下状态之一：

| 展示文案 | 数据库存储值 | 建议颜色 | 含义 |
| --- | --- | --- | --- |
| 满意 | `satisfied` | 绿色 `#22C55E` | 当日进展达到或超过个人预期 |
| 一般 | `average` | 黄色 `#F59E0B` | 基本完成，但仍有明显改进空间 |
| 不满意 | `dissatisfied` | 红色 `#EF4444` | 当日进展明显未达到个人预期 |
| 其他 | `other` | 灰色 `#9CA3AF` | 前三种状态均不适用，说明填写在日报“其他说明”中 |

规则：

- 自我评价状态为必填项。
- “其他”状态不再增加独立的评价备注字段；需要补充的原因统一填写在日报“其他说明”中。
- 未提交日报的看板单元格使用白色，不属于自我评价状态。
- 看板颜色、状态文字、邮件统计均直接来源于自我评价状态，不再由任何时间字段计算。
- 系统不再采集、展示、统计或评分 `work_time` 和 `effective_time`。

### 5.3 日报内容

每份日报保留现有三项文本内容，仅调整名称：

- 业务日期：系统计算，必填；
- 自我评价状态：单选，必填；
- 今日总结：可选，不限制业务字数；
- 明日计划：可选，不限制业务字数；
- 其他说明：可选，不限制业务字数，可填写遇到的困难、需要的支持、风险、备注等；
- 创建时间和最后更新时间：系统生成。

### 5.4 用户状态

- 用户状态分为“启用”和“停用”。
- 停用用户不能登录、提交日报或访问业务数据。
- 停用不删除历史日报，但停用学生不再出现在当前或历史月份的看板中。
- 停用学生的历史日报仅保留在数据库中，普通学生无法再通过看板或人员详情入口访问。
- 删除采用“停用优先”；如确需永久删除，应提供二次确认并记录审计信息。

## 6. 功能需求

### 6.1 登录与会话

#### FR-AUTH-001 学生登录

- 学生继续使用当前系统的用户名和密码登录，不使用 Supabase Auth。
- 学生密码使用安全哈希保存在学生业务表中，禁止保存明文。
- 登录成功后进入日报看板。
- 登录失败时显示统一错误，不泄露账号是否存在。
- 停用用户登录时显示“账号已停用，请联系管理员”。

#### FR-AUTH-002 学生会话保持

- 保持当前“服务端会话 + Cookie”的使用体验，由 Netlify Functions 实现。
- 刷新页面后，在 Session 有效期内保持登录状态。
- Session 过期时返回登录页。
- Session 固定有效期为 30 天，自登录成功时起计算；首期不采用滑动续期。
- 生产 Cookie 必须设置 `HttpOnly`、`Secure` 和 `SameSite=Lax`。
- Netlify Redirect 将 `/api/*` 转发到同站 Functions，避免学生 Session 跨站 Cookie。
- 登录 Function 通过服务端 Supabase 凭据查询 `students`，浏览器不能读取密码哈希。
- 密码验证成功后生成不可预测的随机 Session Token；Cookie 保存原 Token，`student_sessions` 只保存 Token 哈希。
- 每个受保护 Function 通过共用鉴权模块校验 Token、过期时间和学生启用状态。
- 修改密码、管理员停用账号或主动退出时撤销相关 Session。
- 登录接口必须进行频率限制；写操作校验请求 `Origin`，并视实现增加 CSRF Token。
- 未登录用户访问受保护路由时跳转至登录页。

#### FR-AUTH-003 学生退出登录

- 用户可主动退出。
- 退出后清除本地会话并返回登录页。

#### FR-AUTH-004 学生修改本人密码

- 用户可在个人设置中修改密码。
- 新密码规则沿用当前学生账号策略；建议最低 8 位。

#### FR-AUTH-005 管理员登录

- 管理员使用独立管理员登录页和 Supabase Auth。
- 管理员身份应与 Supabase Auth 用户绑定，并在服务端校验管理员白名单或角色。
- 管理员登录状态与学生 Session 互相独立，不允许用学生账号进入管理端。
- 管理员退出时清除 Supabase Auth 会话。

### 6.2 日报填写

#### FR-REPORT-001 加载今日日报

- 进入填写页时加载当前业务日期已有日报。
- 若当日无日报，可将上一业务日的“明日计划”预填为“今日总结”，但不自动提交。

#### FR-REPORT-002 选择自我评价

- 使用单选卡片或单选按钮展示四种状态。
- 每个选项同时展示文字，不得只依赖颜色传达含义。
- “其他说明”始终作为日报正文的第三个输入框显示，不与自评状态联动隐藏。

#### FR-REPORT-003 新增或更新日报

- 用户提交当日内容后，系统按“用户 + 业务日期”执行新增或更新。
- 提交过程中按钮不可重复点击。
- 成功后显示明确反馈并刷新看板。
- 失败时保留用户已输入内容，并给出可理解的错误信息。

#### FR-REPORT-004 内容校验

- 自我评价必填。
- 今日总结、明日计划、其他说明均不设置业务字数上限。
- 为防止异常大请求拖垮服务，可在 HTTP/数据库层设置仅用于安全防护的请求体上限；该上限不作为页面字数限制提示。
- 输入按纯文本或安全 Markdown 处理，禁止执行脚本。

### 6.3 日报看板

#### FR-BOARD-001 月份切换

- 默认展示当前自然月。
- 页面提供“上个月”“下个月”和“回到本月”操作。
- 标题显示当前月份，例如“2026 年 7 月”。
- 一次只请求和渲染一个月的数据；切换月份后重新请求对应月数据。
- 不在主看板提供任意起止日期输入，降低使用复杂度。

#### FR-BOARD-002 状态展示

- 看板视觉参考 GitHub Contributions：每位学生显示一个当月活动卡片。
- 每个学生卡片包含姓名和 7×5/6 的月历方格，按星期排列日期。
- 桌面端可多列排列学生卡片；移动端单列排列。
- 已提交日期方格使用自评状态对应背景色，并提供状态文字的 Tooltip/无障碍标签。
- “其他”状态使用灰色背景。
- 未提交日期使用白色；不属于当前月份的补位格使用透明或浅边框，不作为未提交统计。
- 当月未来日期保持白色，但不得计入“未提交”统计。
- 不再显示“工作时间/有效时间”的数字组合。
- 页面提供状态图例，并保证颜色对比度和无障碍可识别性。
- 支持按学生姓名快速搜索，以便学生人数较多时定位。

#### FR-BOARD-003 日报详情

- 点击已提交单元格打开详情弹窗或详情页。
- 展示姓名、日期、自我评价、今日总结、明日计划、其他说明和更新时间。
- 不展示工作时间、有效时间或基于时间计算的颜色评价。

#### FR-BOARD-004 单人时间段工作详情

- 用户可从看板点击学生姓名，或通过独立入口选择某一学生。
- 页面支持选择开始日期和结束日期，查询该学生在该时间段内的全部日报。
- 结果按日期倒序或正序连续列在同一页面，默认倒序，并允许切换排序方向。
- 每日内容以卡片、时间线或分节方式展示日期、自我评价、今日总结、明日计划和其他说明。
- 未提交日期默认不生成空卡片；可提供“显示未提交日期”开关。
- 页面顶部显示学生姓名、查询区间、提交天数以及各自评状态数量。
- 支持浏览器打印样式；首期不强制提供 PDF/Excel 导出。
- 查询区间必须分页或限制，默认最近 30 天，单次最多 366 天。
- 移动端采用单列卡片/时间线，避免横向表格。

### 6.4 月度活动图组件选型

首选方案是自建轻量 `MonthActivityCalendar` React 组件，不引入 TanStack Table：

- 单月最多 42 个日期格，数据量很小，不需要表格虚拟化。
- 使用 CSS Grid 实现 7×5/6 月历布局，直接映射四种状态颜色。
- 自建组件更容易准确处理月外补位格、未来日期、白色未提交、灰色“其他”和点击详情。
- 组件只接收 `month`、`reports`、`onDayClick` 等数据属性，不直接发请求，方便 Web 与未来移动端复用业务模型。

可选方案是参考或封装 `react-activity-calendar` / `react-contribution-calendar`。这类组件能快速获得 GitHub 风格，但通常按连续日期或年度贡献设计；本项目只显示单月、每位学生一张卡，定制月外补位和状态语义后，自建组件反而更简单。

选型结论：不引入 TanStack；优先自建月度贡献格组件，仅借鉴 GitHub Contributions 的视觉和交互。

### 6.5 管理员模块

#### FR-ADMIN-001 管理入口与鉴权

- 仅管理员可见“用户管理”导航入口。
- 非管理员直接访问 `/admin/users` 时返回无权限页面或跳转。
- 管理页使用 Supabase Auth；服务端必须验证 Supabase JWT 并再次校验管理员角色，不能只依赖前端隐藏按钮。

#### FR-ADMIN-002 用户列表

- 展示学生姓名、用户名、账号状态、创建时间、最近登录时间。
- 支持按姓名或用户名搜索。
- 支持按状态筛选。
- 支持分页，默认每页 20 条。

#### FR-ADMIN-003 创建用户

- 管理员填写学生姓名、唯一用户名、初始密码和账号状态。
- 学生账号创建在现有学生业务表中，不创建 Supabase Auth 用户。
- 初始密码不得以明文保存或回显；写入前使用当前安全哈希方案。
- 建议要求学生首次登录后修改初始密码。

#### FR-ADMIN-004 编辑用户

- 管理员可修改学生姓名和用户名。
- 用户名修改后，下一次登录使用新用户名；已有学生 Session 可按安全策略立即失效。

#### FR-ADMIN-005 启用或停用用户

- 管理员可停用或重新启用用户。
- 操作前需要二次确认。
- 禁止管理员停用自己，除非存在明确的交接机制。

#### FR-ADMIN-006 密码重置

- 管理员可以随时为学生重置密码。
- 管理员设置或重置后的密码一律视为临时密码，学生下次登录后必须先修改密码，完成前不得访问其他业务页面。
- 重置密码时立即撤销该学生全部已有 Session。
- 管理员界面不能读取、显示或导出用户密码。

#### FR-ADMIN-007 删除用户

- 首期默认以停用代替删除。
- 若提供永久删除，仅管理员可操作，并需明确告知历史日报的处理方式。
- 推荐保留日报并将用户资料匿名化；不得因误操作级联删除全部历史日报。

#### FR-ADMIN-008 操作审计

- 创建、编辑、启停、角色变更、密码重置和删除均写入审计日志。
- 日志记录操作者、目标用户、动作、时间和必要的变更摘要。
- 审计日志不记录密码、令牌或密钥。

### 6.6 每日邮件汇总

每日邮件为必须实现的系统功能：

- 数据从 Supabase 查询，不再读取 SQLite。
- 沿用当前项目中的 SMTP：默认 `smtp.exmail.qq.com:465`，使用 SMTP SSL；发件账号和授权密码继续通过 `EMAIL_ADDRESS`、`EMAIL_PASSWORD` 环境变量配置。
- 每个学生必须维护唯一邮箱；每日邮件实时发送给全部启用学生，不再维护独立收件人名单。
- 群发使用 BCC，避免学生之间暴露邮箱地址。
- 邮件统计满意、一般、不满意、其他及未提交人数。
- 明细显示自我评价状态，不显示工作时间或有效时间。
- 使用 Netlify Scheduled Function 每日定时生成并发送汇总邮件。
- 邮件任务失败必须记录结构化日志并触发可观察的失败状态，允许管理员手动补发指定日期邮件。
- 邮件发送凭据仅保存在服务端环境变量中。

## 7. 页面与导航需求

### 7.1 页面清单

| 页面 | 路由建议 | 访问角色 | 主要内容 |
| --- | --- | --- | --- |
| 学生登录页 | `/login` | 匿名 | 用户名、密码、登录 |
| 管理员登录页 | `/admin/login` | 匿名 | Supabase Auth 管理员登录 |
| 日报看板 | `/dashboard` | 学生/管理员 | 月份翻页、状态图例、学生月度贡献格、详情 |
| 填写日报 | `/reports/today` | 学生/管理员 | 四档自评、工作内容、计划、困难 |
| 个人工作详情 | `/people/:studentId/reports` | 学生/管理员 | 某学生在指定时间段内的全部工作详情 |
| 个人设置 | `/profile` | 学生/管理员 | 姓名展示、修改密码 |
| 用户管理 | `/admin/users` | 管理员 | 查询、新增、编辑、启停、重置密码 |
| 无权限页 | `/403` | 已登录用户 | 权限不足说明和返回入口 |

### 7.2 响应式要求

- 支持桌面和手机浏览器。
- 月度贡献格在窄屏保持完整可读，每位学生卡片占一行，不依赖横向滚动。
- 表单控件在手机上单列显示，点击区域不小于 44×44 px。
- 移动端默认提供“按人查看”和日期卡片模式；桌面矩阵作为增强视图。
- 所有查询能力由稳定的 JSON API 提供，前端组件不依赖桌面专属返回结构。

## 8. 数据需求与 Supabase 设计

### 8.1 `students` 学生账号表

学生不使用 Supabase Auth，账号资料继续由业务表维护，但表从 SQLite 迁移到 Supabase PostgreSQL。

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | `bigint` 或 `uuid` | PK | 学生标识；迁移期可保留旧整数 ID |
| `name` | `text` | NOT NULL | 展示姓名 |
| `username` | `text` | UNIQUE，NOT NULL | 学生登录用户名 |
| `email` | `text` | 业务必填、唯一 | 每日汇总邮件接收邮箱 |
| `password_hash` | `text` | NOT NULL | 安全密码哈希，禁止明文 |
| `status` | `text`/enum | NOT NULL，默认 `active` | `active` 或 `disabled` |
| `must_change_password` | `boolean` | NOT NULL，默认 `false` | 是否强制修改临时密码 |
| `last_login_at` | `timestamptz` | 可空 | 最近登录时间 |
| `created_at` | `timestamptz` | NOT NULL | 创建时间 |
| `updated_at` | `timestamptz` | NOT NULL | 更新时间 |

Netlify 登录 Function 负责校验学生用户名、密码哈希和状态，并建立学生 Session。

### 8.2 `student_sessions` 学生会话表

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | `uuid` | PK | 会话标识 |
| `student_id` | 与 `students.id` 一致 | FK，NOT NULL | 所属学生 |
| `token_hash` | `text` | UNIQUE，NOT NULL | 随机会话令牌的哈希，不保存原令牌 |
| `expires_at` | `timestamptz` | NOT NULL | 过期时间 |
| `created_at` | `timestamptz` | NOT NULL | 创建时间 |
| `last_seen_at` | `timestamptz` | 可空 | 最近使用时间 |

登录成功后生成至少 256 位随机令牌，原令牌仅写入 `HttpOnly` Cookie，数据库只保存哈希。退出、密码重置、账号停用时应撤销相关会话。

### 8.3 `admin_profiles` 管理员资料表

管理员身份来自 Supabase Auth 的 `auth.users`，业务角色放在 `public.admin_profiles`。

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | `uuid` | PK，FK → `auth.users.id` | 管理员 Auth 用户 |
| `name` | `text` | NOT NULL | 管理员显示姓名 |
| `status` | `text`/enum | NOT NULL，默认 `active` | `active` 或 `disabled` |
| `created_at` | `timestamptz` | NOT NULL | 创建时间 |
| `updated_at` | `timestamptz` | NOT NULL | 更新时间 |

### 8.4 `daily_reports` 日报表

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | `uuid` | PK | 日报标识 |
| `student_id` | 与 `students.id` 一致 | FK → `students.id`，NOT NULL | 所属学生 |
| `report_date` | `date` | NOT NULL | 业务日期 |
| `self_evaluation` | `text`/enum | NOT NULL | 四种状态之一 |
| `today_summary` | `text` | 可空 | 今日总结，不设业务字数限制 |
| `tomorrow_plan` | `text` | 可空 | 明日计划，不设业务字数限制 |
| `other_notes` | `text` | 可空 | 其他说明，含困难、支持需求等 |
| `created_at` | `timestamptz` | NOT NULL | 创建时间 |
| `updated_at` | `timestamptz` | NOT NULL | 更新时间 |

关键约束：

- 唯一索引：`unique(student_id, report_date)`；
- 日期查询索引：`index(report_date)`；
- 组合索引：`index(student_id, report_date desc)`，用于单人时间段详情；
- `self_evaluation` 仅允许 `satisfied`、`average`、`dissatisfied`、`other`；
- 三个内容字段使用 PostgreSQL `text`，不设置产品层字符数约束。

### 8.5 `admin_audit_logs` 审计表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `uuid` | 日志标识 |
| `actor_id` | `uuid` | 操作管理员 |
| `target_student_id` | 与 `students.id` 一致 | 目标学生，可空 |
| `action` | `text` | 动作类型 |
| `change_summary` | `jsonb` | 不含敏感数据的变更摘要 |
| `created_at` | `timestamptz` | 操作时间 |

### 8.6 邮件配置表

必须建立 `notification_recipients`，字段包含邮箱、显示名称、是否启用、创建时间和更新时间。仅管理员可维护，普通用户不可读取。

必须建立 `notification_runs`，记录目标日期、任务状态、尝试次数、收件人数、错误摘要、开始和结束时间，用于失败追踪和手动补发幂等控制。

### 8.7 数据访问与 RLS 要求

- 学生浏览器不直接访问 Supabase 表；学生的所有读写均通过 Netlify Functions 和学生 Session 鉴权。
- Functions 使用仅存在于服务端的 Supabase 凭据访问 `students`、`student_sessions` 与 `daily_reports`。
- `admin_profiles`：启用 RLS，管理员只能读取自己的管理员资料；管理员资格由数据库策略和服务端共同确认。
- 管理端用户管理操作必须通过受保护的服务端接口，不允许前端直接更新学生密码哈希。
- `admin_audit_logs`：仅管理员可读取；日志仅允许可信服务端写入。
- 管理员身份不能仅信任客户端传入值，应由 Supabase JWT 和 `admin_profiles` 双重判断。

## 9. 系统架构与部署需求

### 9.1 目标架构

```text
浏览器
  └─ Netlify CDN / React SPA
       ├─ 学生端 → 同域 `/api/*` → Netlify Functions → 学生 Session
       └─ 管理端 → Supabase Auth → Netlify 管理 Functions

Netlify Functions（TypeScript）
  ├─ 学生登录、会话、退出与日报 API
  ├─ 管理员 JWT/角色校验与学生账号管理
  ├─ 面向桌面端和移动端的统一 JSON API
  └─ Netlify Scheduled Function（每日邮件任务）

Supabase
  ├─ PostgreSQL
  ├─ Auth（仅管理员）
  ├─ 管理端 RLS / Database Functions
  └─ Migration / Backup
```

### 9.2 Netlify 要求

- 站点连接 `duxy-me/student-simple-daily-report` 的生产分支。
- 前端基准目录建议为 `frontend`，构建命令为 `npm run build`，发布目录为 `frontend/build`（具体相对路径按 Netlify 配置校验）。
- 配置 SPA fallback：所有前端路由重写至 `/index.html`。
- Pull Request 使用 Deploy Preview，生产分支合并后自动发布。
- 环境变量至少包含：
  - `REACT_APP_SUPABASE_URL`；
  - `REACT_APP_SUPABASE_ANON_KEY`（仅管理员认证）；
  - 服务端 Functions 使用的 Supabase URL 与受保护服务凭据；
  - 学生 Session Cookie 名称、有效期等服务端配置。
- 使用 Netlify Redirect 将 `/api/*` 映射到 Functions，使学生端 Cookie 保持同站。
- `SUPABASE_SERVICE_ROLE_KEY` 只能配置在服务端函数作用域，严禁使用 `REACT_APP_` 前缀或打入浏览器包。
- 正式域名启用 HTTPS；Supabase Auth 的 Site URL 和 Redirect URL 必须加入正式域名及必要的预览域名。

### 9.3 Supabase 要求

- 开发、测试、生产环境应使用独立项目或至少独立的受控数据环境。
- 建表、约束、索引、函数和 RLS 均通过 SQL Migration 管理。
- 开启数据库备份能力，并定期验证恢复流程。
- 匿名密钥可以出现在前端，但仅用于管理员认证；学生业务表不允许匿名直连。
- 服务角色密钥仅用于可信服务端，不得写入 Git、日志或浏览器存储。

### 9.4 新系统实现边界

新系统按 TypeScript Netlify Functions 重新实现，不兼容旧 Flask 运行平台、旧接口、旧 Session、旧密码哈希或旧 SQLite 数据格式。

- 不提供旧 `/api/*` 到新 `/api/v1/*` 的兼容层；
- 不迁移旧 Session 或复用旧密码哈希；
- 学生账号由管理员在新系统创建或批量初始化，并使用强制修改的临时密码；
- 新密码使用成熟的 Argon2id、scrypt 或 bcrypt 实现；
- 新系统上线后独立运行，不设计回切旧平台的数据同步。

## 10. 接口与服务边界

### 10.1 普通业务操作

学生业务统一通过 TypeScript Netlify Functions JSON API 实现：

- 学生用户名密码登录、Session 检查和退出；
- 获取有效学生列表；
- 按月份获取看板日报；
- 获取某学生某日详情；
- 获取某学生在指定时间段内的连续工作详情；
- 新增或更新本人日报。

### 10.2 特权操作

管理员操作通过 Netlify 管理 Functions 实现，Functions 验证 Supabase Auth JWT：

- 创建、编辑、启停学生业务账号；
- 设置学生临时密码；
- 删除或匿名化学生账号；
- 写入管理员审计日志；
- 使用服务角色查询或执行定时邮件任务。

所有特权接口必须：

- 校验 Bearer Token；
- 校验调用者为有效管理员；
- 校验输入参数；
- 返回统一错误结构；
- 不在响应或日志中暴露密钥、密码和完整令牌。

### 10.3 API 版本与移动端接口预留

- 所有接口统一使用 `/api/v1` 前缀，不提供旧 `/api` 兼容接口。
- Web 端与未来移动端共用业务 API，不把 HTML、桌面列宽或颜色样式写入响应。
- 日期、状态和正文返回结构保持稳定，状态使用英文枚举，中文文案由客户端映射。
- 列表接口统一支持分页、排序和日期范围参数，并返回 `data`、`meta`、`error` 结构。
- Session Cookie 继续服务当前 Web 学生端；鉴权中间件抽象为 `authenticateStudent(request)`，未来移动端可增加 Bearer Token 适配器，而不修改日报业务服务。
- 不因“预留移动端”在本期开放长期有效学生令牌；令牌方案需单独完成安全设计。

建议接口：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/api/v1/student/session` | 学生登录 |
| `GET` | `/api/v1/student/session` | 获取学生会话 |
| `DELETE` | `/api/v1/student/session` | 学生退出 |
| `GET` | `/api/v1/students` | 获取看板学生 |
| `GET` | `/api/v1/reports?month=YYYY-MM` | 获取单月看板日报 |
| `GET` | `/api/v1/students/{id}/reports?start_date=&end_date=&page=&page_size=` | 单人时间段工作详情 |
| `GET` | `/api/v1/students/{id}/reports/{date}` | 单人单日日报详情 |
| `PUT` | `/api/v1/reports/{date}` | 新增或更新本人日报 |
| `GET` | `/api/v1/admin/students` | 管理员查询学生 |
| `POST` | `/api/v1/admin/students` | 管理员创建学生 |
| `PATCH` | `/api/v1/admin/students/{id}` | 管理员编辑或启停学生 |
| `POST` | `/api/v1/admin/students/{id}/temporary-password` | 管理员设置临时密码 |

## 11. 非功能需求

### 11.1 性能

- 常规页面首屏在良好网络条件下 3 秒内可交互。
- 单月看板查询 2 秒内返回。
- 用户列表和日报查询必须分页或限制范围，避免无界查询。
- 数据库查询使用必要索引，避免按每个单元格分别请求详情的 N+1 问题。

### 11.2 安全

- 全站 HTTPS。
- 学生密码使用成熟的慢哈希算法存入业务表；管理员密码由 Supabase Auth 管理。
- 学生业务表不向浏览器开放 Supabase 直连；管理端相关表启用 RLS 并编写授权测试。
- 富文本/Markdown 输出必须清理危险 HTML。
- 管理员操作具备审计记录和二次确认。
- CORS、Auth Redirect URL 按生产域名收紧。
- 依赖和密钥定期更新；日志禁止包含个人密码和令牌。

### 11.3 可用性与可访问性

- 状态不能只用颜色表示，必须同时显示文字或可访问标签。
- 错误提示与具体字段关联。
- 键盘可完成登录、填写、查看详情和管理员操作。
- 成功和失败反馈可被屏幕阅读器感知。

### 11.4 兼容性

- 支持最新两个主要版本的 Chrome、Edge、Firefox 和 Safari。
- 支持常见手机浏览器和 360 px 以上视口宽度。

### 11.5 可维护性

- 数据库 Schema 和 RLS 策略纳入版本控制。
- 状态枚举、显示名称和颜色集中配置，避免前后端多处硬编码。
- 关键业务规则具备自动化测试。
- Netlify 构建失败不得影响当前线上版本。

### 11.6 隐私与数据保留

- 学生仅收集姓名、用户名和日报内容；管理员认证由 Supabase Auth 保存必要的管理员邮箱。
- 明确账号停用、永久删除和历史日报保留策略。
- 数据导出或删除请求由管理员按组织制度处理。

## 12. 新系统初始化方案

新系统不兼容或迁移旧平台数据，初始化范围如下：

1. 通过 SQL Migration 创建 Supabase Schema、约束、索引和 RLS。
2. 创建首个 Supabase Auth 管理员及 `admin_profiles` 记录。
3. 管理员通过后台逐个创建学生，或使用一次性批量初始化脚本。
4. 所有学生初始密码均标记 `must_change_password = true`。
5. 初始化邮件收件人表并配置当前项目正在使用的 SMTP 环境变量。
6. 执行学生登录、强制改密、日报、历史互看、停用隐藏和每日邮件端到端验收。

新系统中的“历史信息”指新系统上线后累计保存的全部日报，不包含旧平台历史数据。

## 13. 验收标准

### 13.1 登录与权限

- 有效学生可以登录；错误密码和停用账号不能登录。
- 学生不能访问管理员页面或管理员接口。
- 学生不能新增、修改或删除他人的日报。
- 管理员可以访问用户管理，并且所有操作留下审计记录。

### 13.2 日报

- 表单只提供满意、一般、不满意、其他四种自评状态。
- 页面和接口均不再要求 `work_time`、`effective_time`。
- “其他”为灰色，“未提交”为白色，两者文字和视觉均可区分。
- 今日总结、明日计划和其他说明均不显示字数上限。
- 同一用户同一天重复提交后只有一条记录且内容被更新。
- 凌晨 03:00 前后的业务日期计算符合 `Asia/Shanghai` 规则。

### 13.3 看板

- 单元格展示状态文字和对应颜色，不显示工时数字。
- 未提交与四种自评状态能够明确区分。
- 点击已提交单元格可查看完整日报，且详情无时间评分。
- 上月、下月和回到本月操作正常，手机端学生卡片单列展示。
- 可以选择某个学生和时间段，把该范围内全部工作详情连续展示在一页。
- 移动端默认使用卡片/按人视图，接口与桌面端共用。

### 13.4 管理员模块

- 管理员可搜索、筛选、创建、编辑、停用和启用用户。
- 学生用户名重复时创建失败并显示明确错误。
- 管理员可以设置学生临时密码，但看不到原密码或密码哈希。
- 最后一个有效管理员不能被停用或降级。

### 13.5 部署与安全

- Netlify 正式域名可通过 HTTPS 访问，刷新任意 SPA 路由不会 404。
- Supabase 数据持久化正常，重新部署 Netlify 不丢失数据。
- 浏览器构建产物中不存在 `service_role` 密钥。
- 未授权请求被 RLS 或特权接口拒绝。
- Deploy Preview 与生产环境配置隔离。

## 14. 测试范围

- 单元测试：业务日期、自评校验、文本长度、状态映射。
- 数据库测试：唯一约束、Check Constraint、RLS 的允许与拒绝场景。
- 集成测试：登录、日报 Upsert、用户邀请、停用、密码重置。
- 端到端测试：学生完整流程、管理员完整流程、跨角色越权测试。
- 初始化测试：管理员、学生临时密码、SMTP 收件人、时区日期和异常数据处理。
- 部署测试：Netlify 构建、SPA 路由、环境变量、Auth 回调。

## 16. 风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 将前端匿名密钥误认为可访问学生业务表 | 数据越权 | 学生业务仅经 Netlify Functions；管理端表启用 RLS，并进行越权测试 |
| `service_role` 泄露到前端 | 全库高权限泄露 | 仅放在服务端函数环境变量，扫描构建产物和 Git 历史 |
| 初始学生账号或临时密码配置错误 | 学生无法首次登录 | 使用初始化校验、强制改密和管理员随时重置 |
| 管理员 Auth 身份与管理员资料不一致 | 管理端无法登录或越权 | 管理员开通采用幂等写入、白名单校验和审计日志 |
| Session Cookie 或 Redirect 配置错误 | 学生无法保持登录 | API 使用同站 `/api/*` 路径，Cookie 设置 `HttpOnly`、`Secure`、`SameSite=Lax` |
| 管理员误停用唯一管理员 | 系统失去管理入口 | 服务端强制检查最后一个有效管理员 |
| Netlify 与 Supabase 回调域名不一致 | 登录/重置失败 | 同步配置生产域名和受控的预览回调地址 |
| 免费套餐限制或休眠 | 可用性下降 | 上线前核对配额，设置监控并制定升级阈值 |

## 17. 已确认的产品决策

1. 学生可以查看所有启用学生在新系统中的全部历史日报和完整正文。
2. 停用学生不再出现在任何月份的看板或人员详情入口。
3. 学生 Session 固定有效 30 天，不滑动续期。
4. 管理员可以随时重置学生密码；所有管理员设置的密码均为临时密码并强制首次修改。
5. 每日邮件必须实现，沿用当前项目 SMTP 服务器配置。
6. 新系统不兼容旧平台、旧接口、旧 Session、旧密码哈希或旧数据格式。

- 生产页面不再采集或展示时间评分；
- 管理员模块具备服务端权限校验和审计能力；
- Netlify 生产部署成功，Supabase 生产数据读写正常；
- 密钥扫描、越权测试、初始化核对和用户验收通过；
- 上线、回滚、备份恢复和管理员操作说明已形成文档。

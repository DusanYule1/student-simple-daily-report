## 1. Netlify："接口不存在"（404）但接口明明存在

**现象**：管理员登录页点登录，提示"接口不存在"；`/api/v1/admin/session` 直接 curl 也 404。

**排查**：下载已部署的前端产物 `main.xxx.js`，搜索发现 `process.env.REACT_APP_SUPABASE_URL` 以**字面量原样**存在于产物中——说明构建时该环境变量为空。

**根因**：两层问题叠加：

1. **CRA 的 `REACT_APP_*` 变量是构建时烧进静态 JS 的**，不是运行时读取。构建之后才在 Netlify 加变量无效，必须 Trigger deploy 重新构建。
2. 前端需要的是 `REACT_APP_SUPABASE_URL` / `REACT_APP_SUPABASE_ANON_KEY`（**带前缀**），与后端 Functions 用的 `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY`（**不带前缀**）是**不同的变量名**。只配后端那对，前端照样判定"未配置"。

前端判定逻辑（`frontend/src/services/supabase.js`）：两个 `REACT_APP_SUPABASE_*` 任缺一个 → `isAdminAuthConfigured=false` → 前端误认为本地模式 → 调本地专用接口 `/admin/session`（生产环境路由里该接口仅本地模式存在，故 404）。

**修复**：Netlify 补两个前端变量 → **必须重新部署** → 浏览器 Ctrl+Shift+R 强刷。

```
REACT_APP_SUPABASE_URL=https://your-project.supabase.co
REACT_APP_SUPABASE_ANON_KEY=<Publishable key，sb_publishable_ 开头>
```

**教训**：`REACT_APP_*`（前端浏览器用）和裸名（服务端用）是两套独立变量，值可以相同但名字必须都配。

## 2. Supabase 迁移：`42P13 cannot change return type of existing function`

> ⚠️ 历史记录：very_satisfied 功能已于 2026-09-05 整体回退（代码 + 迁移文件删除），且 Supabase 计划全量重建，以下两个问题（§2/§3）在新库上不会再出现。保留排查过程供未来参考。

**现象**：跑第 5 个迁移（`202609010001_very_satisfied.sql`）报错：

```
ERROR: 42P13: cannot change return type of existing function
HINT: Use DROP FUNCTION get_monthly_board(date,date,text) first.
```

**根因**：PostgreSQL 的 `CREATE OR REPLACE` **不允许改变函数返回表的 OUT 行类型**。第 2 个迁移已建了旧签名的 `get_monthly_board`（无 `very_satisfied_count` 列），第 5 个想加列就被拒。

**修复**（两步，分两次 Run）：

```sql
-- 第 1 次 Run
alter type public.self_evaluation add value if not exists 'very_satisfied';
drop function if exists public.get_monthly_board(date, date, text);
```

```sql
-- 第 2 次 Run：完整执行 202609010001_very_satisfied.sql 的 create function ... grant 部分
```

**为什么必须拆两次**：见下一条。

## 3. Supabase 迁移：`55P04 unsafe use of new value of enum type`

**现象**：把 `alter type ... add value 'very_satisfied'` 和函数体（内含 `where r.self_evaluation = 'very_satisfied'`）放在**同一次 Run** 里执行，报：

```
ERROR: 55P04: unsafe use of new value "very_satisfied" of enum type
HINT: New enum values must be committed before they can be used.
```

**根因**：SQL Editor 每次 Run 是一个事务；PostgreSQL 限制**同一事务内**新增的枚举值不能被引用。必须先提交 `alter type`（第 1 次 Run），再跑引用新值的语句（第 2 次 Run）。

**注意**：报错时整个事务回滚，库不会处于半迁移状态——但**别因此重复整跑**，按上面两步走即可。

**验证是否成功**（用 curl + service_role key 只读验证）：

```bash
# 枚举值生效 → HTTP 200；未生效 → 22P02 invalid input value
curl -H "apikey: $KEY" -H "Authorization: Bearer $KEY" \
  "$SUPABASE_URL/rest/v1/daily_reports?self_evaluation=eq.very_satisfied&select=id&limit=1"

# 函数新签名可用 → HTTP 200 返回 []
curl -X POST "$SUPABASE_URL/rest/v1/rpc/get_monthly_board" \
  -H "apikey: $KEY" -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"p_month_start":"2026-09-01","p_next_month_start":"2026-10-01"}'
```

## 4. Supabase 新版密钥体系：Secret keys vs Publishable key

2025 年底 Supabase 改版后，Settings → API Keys 里只有两项：

| 界面显示 | 旧名 | 用途 | 填到哪 |
|---|---|---|---|
| **Publishable key**（`sb_publishable_...`） | anon key | 前端用，受 RLS 限制 | Netlify 的 `REACT_APP_SUPABASE_ANON_KEY` |
| **Secret keys**（`sb_secret_...`，需手动 Create） | service_role key | 管理员级，绕过 RLS | Netlify 的 `SUPABASE_SERVICE_ROLE_KEY`、本地 `.env` |

**踩坑点**：

- Secret key **创建时只显示一次**，必须立刻复制，关掉弹窗只能重新生成。
- Secret key **能做 DML 不能做 DDL**：`bootstrap:admin` 报 `PGRST205 Could not find the table 'public.admin_profiles'` 就是因为迁移（建表）还没跑——先跑完 5 个 SQL，再跑 bootstrap。
- `bootstrap:admin` 幂等：Auth 用户已存在就跳过创建，只 upsert `admin_profiles`。中途失败的可以先查 `auth.users` 确认哪半步完成了。
- **Legacy API keys 区块不用管**，新 secret key 与 supabase-js 完全兼容。

## 5. Netlify 站点访问保护导致全站 401

**现象**：站点所有路径（页面+API）都返回 401 + 一个 "Login Redirect" HTML，跳 `app.netlify.com/edge-access?domain=...`。前端表现为"接口不存在"。

**根因**：Netlify 开了站点级访问保护（Password protection / 限团队成员可见）。

**修复**：Site configuration → **Access and visibility** → Site visibility 改为 **Public**。即时生效，无需重新部署。

**识别特征**：401 响应体是含 `edge-access` 的 HTML 重定向脚本 → 是 Netlify 平台拦截，不是应用代码。

## 6. 管理员密码的硬校验

`scripts/bootstrap-admin.mts` 强制 `BOOTSTRAP_ADMIN_PASSWORD` **≥12 字符**（纯代码校验，与 Supabase 自身要求无关）。10 位纯数字会被拒：

```
Error: BOOTSTRAP_ADMIN_PASSWORD must contain at least 12 characters
```

密码不落入任何业务表：Supabase `auth.users.encrypted_password` 存 bcrypt 哈希，`admin_profiles` 只有 id/name/status，**Dashboard 里看不到明文属正常现象**。

## 7. 本机环境坑（NFS + 网络 + 认证）

### 7.1 NFS 软挂载

- 项目在 NFS（`soft,nolock`）上，git 操作偶发 `uv_cwd` 失败 → 用 bash 的 `workdir` 参数或 `git -C <repo>`，别依赖当前目录。
- git checkout 搞乱索引时：`git reset --hard <已知好commit>`。
- **SQLite 多进程并发在 NFS 上不可靠**（WAL 锁瞬断 → "unable to open database file"）：禁止同时跑两个 `npm run dev:local`；代码里 `getLocalDb` 已加 5 次短退避重试。

### 7.2 网络与 DNS

- 本机对 github.com / supabase.co 的 DNS **偶发解析失败**（`Temporary failure in name resolution`），重试即恢复。curl 报 `HTTP 000` / `Connection reset by peer` 多为代理首连抖动，**先重试 2-3 次再下结论**。
- SSH 连 GitHub 首次用 `ssh -T git@github.com -o StrictHostKeyChecking=accept-new`；成功标志：`Hi <用户名>! You've successfully authenticated`。

### 7.3 Git 身份与 SSH

- 身份是**仓库级**配置（`.git/config`）：`user.email=dusanyule@gmail.com`、`user.name=DusanYule1`。全局 `~/.gitconfig` 为空——新 clone 的其他仓库没有身份，需要时再配。
- GitHub 关联靠**提交邮箱**：历史提交用的 `dusanyule@foxmail.com` 不会算到 GitHub 账号头上（灰头像、不进贡献日历）；想关联可在 GitHub Settings → Emails 添加该邮箱，**无需改写历史**。
- SSH 密钥 `~/.ssh/id_ed25519`（无 passphrase），**跨会话可用**；换机器需拷贝密钥对或重新生成。
- 推送方式：`git push origin production local-preview`（两分支保持同 HEAD）。

## 10. 快速排障决策树

```
登录报"接口不存在"
├─ 响应是 401 + edge-access HTML → Netlify 访问保护没关（§5）
├─ 前端产物里 REACT_APP_SUPABASE_URL 是字面量 → 构建时缺变量，补变量重部署（§1）
└─ 其他 404 → 看响应体 request_id，对照 router.ts 路由表

SQL Editor 报错
├─ 42P13 函数返回类型 → 先 drop function 再建（§2）
├─ 55P04 枚举新值 → alter type 单独一次 Run 先提交（§3）
└─ PGRST205 找不到表 → 迁移没跑完，先跑迁移再 bootstrap（§4）

bootstrap:admin 失败
├─ 密码 <12 位 → 换密码（§6）
├─ PGRST205 → 迁移未完成（§4）
└─ 成功一半 → 脚本幂等，直接重跑
```
